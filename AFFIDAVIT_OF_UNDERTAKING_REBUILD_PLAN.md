## 1. Architecture recap (confirmed)

AU is generated by `ApprovedLoanPdfTemplateService` (`app/Services/LoanRequests/ApprovedLoanPdfTemplateService.php`):
it opens the static base PDF via FPDI/TCPDF (`makePdf()`, line 474: `new Fpdi('P', 'mm', 'A4', ...)` — so
**all field-map coordinates are millimeters on an A4 portrait page, 210×297mm**) and stamps values from
`AffidavitUndertakingPdfFieldMap` (`app/Services/LoanRequests/PdfFieldMaps/AffidavitUndertakingPdfFieldMap.php`)
on top at fixed x/y.

`renderField()` (lines 161–216) supports exactly **three** field types — `text` (default), `check`,
`signature` — dispatched from `field['type']`. **No generic image-overlay type exists or is needed.**
The header logo/title/table/paragraph text for Phase 1 must be baked directly into the base PDF file
itself, matching the existing pattern for AU/UB/Authorization (base PDF holds all fixed artwork; the
field map only stamps variable data).

**Visual verification tool already exists and must be used, not invented:**
`php artisan loan-documents:calibrate-fields au` (`app/Console/Commands/CalibrateApprovedLoanPdfFieldsCommand.php`)
overlays a labeled 10mm grid and colored field-bounding-boxes on top of the live template PDF, writing to
`storage/app/tmp/calibrate-au.pdf`. Use this at every phase that touches artwork or coordinates — do not
rely on "no errors thrown" as verification.

## 5. Open decision: where do Doc/Page/Book/Series/notarial fields conceptually belong?

These are standard PH notarization fields that could plausibly be needed by other documents later
(Loan Security Agreement, GREPALIFE, Promissory Note — PN already has its own "Notarization" section
per `WIBS_DOCUMENT_FIELD_MAP.md:457-470`). Two options, with a recommendation:

**Recommended: add all 8 new fields to the existing `processing` data section** in
`LoanRequestDataService::FIELD_DEFINITIONS` (`app/Services/LoanRequests/LoanRequestDataService.php`),
the same section that already holds `notarial_venue`, `witness_one_name`, `witness_two_name`,
`barangay_official_name`, `barangay_official_title` (lines ~318–357).

**Why this works without a new table:** this codebase stores all `processing`-section fields in a
generic EAV table, `loan_request_data_entries` (migration
`2026_06_15_081803_create_loan_request_data_entries_table.php`, model `App\Models\LoanRequestDataEntry`),
keyed by `field_key` — **not** dedicated columns. `LoanRequestDataService::loadFlatValues()` returns them
flattened by `field_key` regardless of `section`, and `ApprovedLoanDocumentService::buildDocumentData()`
reads `$flatValues['field_key']` the same way regardless of which document is rendering. So:
- **No schema migration is actually required** for these 8 fields (unlike what "migration for new
  column(s)" in the original brief implied) — this corrects that assumption. They register purely as
  new `FIELD_DEFINITIONS` array entries, same as `witness_one_name` etc.
- Any other document's field map (LSA, GREPALIFE, PN) can read the same `field_key`s from the same
  `flatValues` array later **without any wiring changes to this section** — the reusability the brief
  was asking about is already free, by construction of the existing pattern.
- A dedicated new "notarial details" table would duplicate this mechanism for no benefit and is
  **not recommended** — flag as rejected-with-reason in the plan, not silently ignored.

**Trade-off to flag to WIBS/Ariz explicitly:** because `processing` is a single flat section, there is no
schema-level distinction between "AU's notarization fields" and "any other document's notarization
fields" if they're later given the same keys — this is a feature (free reuse) but means naming must stay
generic enough (`doc_number`, not `au_doc_number`) if the intent really is future cross-document reuse.
Confirm this naming with the team before Phase 3 lands; do not wire into any other document in this
plan (out of scope, see §9).
